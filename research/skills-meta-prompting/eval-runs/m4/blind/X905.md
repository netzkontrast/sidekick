Kurz: **Als fertige Warteschlange taugt libx nicht.** Höchstens bietet es eine Wiederaufnahme mit „mindestens einmal“-Semantik, und auch die nur unter Bedingungen. Ob das reicht, hängt an der offenen Frage aus `auftrag.md`, und die muss der Owner beantworten.

## Was tatsächlich drin ist

Das Paket hat genau eine Funktion, `vendor/libx/jobs.py:1-3`:

```python
def resume(db):
    for job in db.query("select id from jobs where status = 'running'"):
        db.execute("update jobs set status = 'queued' where id = ?", job.id)
```

Es gibt kein Einreihen, keinen Worker, kein Abholen und Sperren von Aufgaben, kein Schema für `jobs` und keine Wiederholungs- oder Fehlerlogik. Die eigentliche Warteschlange müssten wir also selbst bauen.

## Befunde

1. **Die README verspricht mehr als der Code tut.** Laut `README.md:7` startet libx Aufgaben mit Status `running` „erneut“. Der Code setzt sie aber nur auf `queued` zurück. Ob sie danach wirklich laufen, hängt an einem Worker, den libx gar nicht mitliefert.
2. **Es gilt „mindestens einmal“, nicht „genau einmal“.** Angenommen, eine Aufgabe ist fertig (Export geschrieben, Erinnerung verschickt), aber der Absturz kommt, bevor der Status auf erledigt steht. Dann läuft sie nach dem Neustart ein zweites Mal. Doppelte Ausführung ist so eingebaut. „Genau einmal“ ließe sich nur erreichen, wenn wir die Aufgaben selbst idempotent machen, zum Beispiel mit einem Idempotenzschlüssel pro Erinnerung.
3. **Mit mehreren Prozessen ist es unsicher.** `resume` setzt *alle* laufenden Aufgaben zurück, auch die, an denen ein anderer Worker gerade noch arbeitet. Dann laufen sie doppelt. Für die Wiederaufnahme ist das nur bei genau einem Worker-Prozess sicher.
4. **Es läuft nicht atomar.** Die Updates laufen einzeln und ohne Transaktion. Stürzt `resume` selbst ab, bleibt ein Teil der Aufgaben zurückgesetzt und der Rest nicht. Im nächsten Lauf wird das zwar nachgeholt, ist aber unsauber.
5. **Die API passt womöglich nicht.** `db.query` und `job.id` gehören nicht zum Standardmodul `sqlite3`, libx erwartet also einen eigenen Wrapper. Außerdem wird `id` als einzelner Wert übergeben, nicht als Tupel. Mit einer rohen `sqlite3`-Verbindung würde das scheitern. Ausgeführt habe ich nichts, das habe ich nur aus dem Code gelesen.

## Entscheidungshilfe

- **Wenn „mindestens einmal“ reicht:** libx lässt sich als kleiner Baustein für die Wiederaufnahme nutzen, mit drei Auflagen: ein Worker-Prozess, Aufgaben idempotent machen, Warteschlange und Worker selbst bauen. Bei Exporten ist doppelte Ausführung meist harmlos. Bei Erinnerungen würden Nutzer sie doppelt bekommen, wenn wir nicht deduplizieren.
- **Wenn „genau einmal“ nötig ist:** Das kann libx nicht leisten. Den Hauptteil der Arbeit (Idempotenz, sauberes Sperren) hätten wir in beiden Fällen selbst zu tragen.

Meine Empfehlung: Wegen drei Zeilen Code lohnt es sich kaum, eine Fremdabhängigkeit aufzunehmen. Die README beschreibt das Verhalten außerdem falsch. Ich würde die Warteschlange direkt bauen und dabei bewusst „mindestens einmal“ plus idempotente Aufgaben wählen, oder zu einer etablierten Bibliothek greifen.
