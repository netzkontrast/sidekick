## Wie man das Senden wirklich abschaltet

| Aussage | README (Herstellerangabe) | Code (gelesen) |
|---|---|---|
| Schalter zum Abschalten | `METRIKFUNK_DISABLE=1` (`README.md:16`) | Der Code prüft nur `METRIKFUNK_OPTOUT === "1"` (`src/client.js:9`). `METRIKFUNK_DISABLE` kommt im Code gar nicht vor. |
| Automatisch aus in CI (`CI=true`) | ja (`README.md:18`) | Im gesamten Repo gibt es keine Prüfung auf `CI`. Gesucht habe ich nach `\bCI\b` und `METRIKFUNK` in allen Dateien. Ohne `METRIKFUNK_OPTOUT` liefert `telemetryEnabled` immer `true` (`src/client.js:10`). |

Was das bedeutet:
- `METRIKFUNK_DISABLE=1` bewirkt nichts.
- Dass die CI-Umgebung `CI=true` setzt, bewirkt ebenfalls nichts.
- Laut Code schaltet nur **`METRIKFUNK_OPTOUT=1`** ab, und zwar nur mit genau dem Wert `"1"`. `true` oder `yes` reichen nicht.
- Die Variable wird bei jedem `track()` aus `process.env` gelesen (`src/client.js:17`). Sie muss also gesetzt sein, solange der Prozess läuft. Beim Start allein reicht nicht.

## Was sonst übertragen würde

Laut README nur „Ereignisname, Zeitstempel und eine zufällige Sitzungs-ID“ (`README.md:14–15`). Laut Code schickt jedes `track()` einen POST an `https://example.invalid/metrikfunk/v1/events` (`src/client.js:5, 26`) mit folgendem Inhalt (`src/client.js:18–25`):
- `app`: der Name der Anwendung
- `name`: der Ereignisname
- **`props`: alle Eigenschaften, die der Aufrufer mitgibt, ungefiltert.** In der CI können das zum Beispiel Pfade oder Testdaten sein.
- `session`: eine Zufalls-ID aus `Math.random`
- **`host`: `os.hostname()`, also der Name des CI-Runners**
- `ts`: der Zeitstempel

`props` und `host` stehen nicht in der README. Netzwerkfehler werden stillschweigend verschluckt (`src/client.js:27`). Ein blockierter oder fehlgeschlagener Versand fällt im CI-Log deshalb nicht auf.

## Empfehlung für die CI

1. Setzt in der Pipeline global `METRIKFUNK_OPTOUT=1`. Das ist die einzige Abschaltung, die im Code vorkommt.
2. Darauf allein solltet ihr euch nicht verlassen, denn ein Update kann den Schalter wieder umbenennen. Sperrt deshalb zusätzlich den ausgehenden Netzverkehr der CI-Jobs, mindestens zu diesem Host, am besten generell per Egress-Regel.
3. Schreibt einen kleinen Test, der festhält, dass `telemetryEnabled({ METRIKFUNK_OPTOUT: "1" })` den Wert `false` liefert. Die Funktion wird exportiert (`src/client.js:33`). So fällt es auf, wenn ein Update den Schalter ändert.

**Empfehlung:** Als Dependency nutzen, aber nur mit beidem: dem Opt-out und der Netzsperre. Die Entscheidung liegt bei euch.
