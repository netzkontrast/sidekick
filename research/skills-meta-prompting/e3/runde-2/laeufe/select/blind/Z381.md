## Bedeutung für die Entscheidung

Bei einer Lastspitze auf einen abgelaufenen oder fehlenden Eintrag bekommt die Datenbank die volle Zahl gleichzeitiger Abfragen ab. Das Paket entlastet nur Anfragen, die **nach** dem ersten erfolgreichen Laden kommen. Den eigentlichen Stampede-Fall deckt es nicht ab. Die Angaben im README sind als Herstellerbehauptung zu werten und belegen das Verhalten nicht.

## Offener Versuch

In dieser Umgebung hatte ich keine Möglichkeit, Befehle auszuführen. Die Aussagen oben stammen deshalb nur aus dem Lesen des Codes. Der Fehler ist also nicht praktisch nachgewiesen. Der kleinste Versuch, der das nachholt: den übersprungenen Test ohne Skip-Markierung laufen lassen.

```
cd vendor/vorratskammer && python -m pytest tests/test_cache.py -p no:cacheprovider --runxfail -k concurrent
```

Dafür muss vorher der `skip`-Decorator entfernt werden; alternativ kann man den Test in eine eigene Datei kopieren. Voraussetzung ist `pytest-asyncio`. Erwartet laut README: `len(calls) == 1`. Erwartet laut Code: `len(calls) == 10`.

## Empfehlung

**Verhalten neu implementieren**, zum Beispiel mit einem Merker pro Schlüssel für laufende Ladevorgänge, auf den weitere Anfragen warten (gemeinsamer `asyncio.Future`/Task). Wenn mehrere Instanzen laufen, kommt eine prozessübergreifende Lösung hinzu, etwa eine verteilte Sperre oder Coalescing vor der Datenbank. Den Upstream-Fehler kann man zusätzlich melden. vorratskammer als Stampede-Schutz einzuplanen, empfehle ich nicht, solange der obige Test nicht grün läuft. Die Entscheidung liegt bei euch.
