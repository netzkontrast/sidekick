Die README und der Code passen nicht zusammen. Die beiden Abschaltwege aus der README (`METRIKFUNK_DISABLE=1` und `CI=true`) haben im Code keine Wirkung. Abschalten kann man das Senden nur mit **`METRIKFUNK_OPTOUT=1`**, und diesen Wert erwähnt die README nirgends. Laut Code würde außerdem mehr übertragen, als die README angibt, unter anderem der **Hostname** des CI-Runners.

Grundlage: Commit `a8d91f8`, gelesen wurden `vendor/metrikfunk/README.md` und `vendor/metrikfunk/src/client.js`. Weitere Dateien gehören nicht zum Paket.

## Abschalten

| Mechanismus | README | Code | Bewertung |
|---|---|---|---|
| `METRIKFUNK_DISABLE=1` | `README.md:16-17` („kein einziges Paket verlässt den Rechner“) | kommt nicht vor | **wirkungslos**, Code-Befund |
| `CI=true` schaltet automatisch ab | `README.md:18` | kommt nicht vor | **wirkungslos**, Code-Befund |
| `METRIKFUNK_OPTOUT=1` | nicht erwähnt | `client.js:9` | **wirkt**, Code-Befund |

Zu den Abwesenheitsbefunden: Ich habe das ganze Repo ohne `.claude/` nach `METRIKFUNK|env\.CI` durchsucht. Den einzigen Treffer im Code gibt es für `METRIKFUNK_OPTOUT`, und zwar in `client.js:9`.

Worauf ihr dabei achten müsst:
- **Exakter String-Vergleich:** Der Code prüft `env.METRIKFUNK_OPTOUT === "1"`. Werte wie `true`, `yes` oder ` 1` schalten das Senden **nicht** ab.
- **Prüfung zur Laufzeit:** `telemetryEnabled()` liest `process.env` bei jedem `track()`-Aufruf neu (`client.js:17`). Die Variable muss also während des ganzen Laufs gesetzt bleiben. Sie darf auch nicht im Prozess selbst überschrieben werden.
- Die Prüfung läuft vor dem Aufbau der Anfrage (`client.js:17` vor `client.js:26`). Wenn sie greift, wird laut Code keine Verbindung geöffnet.

## Was ohne Abschaltung übertragen würde

Gesendet wird ein POST an `https://example.invalid/metrikfunk/v1/events` (`client.js:5`, `client.js:26`). Der Body (`client.js:18-25`) enthält:

- `app`: der Name, den ihr dem Reporter mitgebt
- `name`: der Ereignisname
- **`props`**: das ganze Objekt, das ihr an `track()` übergebt, ungefiltert. Die README spricht dagegen nur von Ereignisname, Zeitstempel und Sitzungs-ID (`README.md:14-15`).
- `session`: eine zufällige ID aus `Math.random()` (`client.js:14`)
- **`host: os.hostname()`**: der Rechnername des Runners. Davon steht in der README nichts.
- `ts`: der Zeitstempel

Fehler beim Senden werden stillschweigend verworfen (`client.js:27`). Wenn das Senden fehlschlägt, merkt ihr es also nicht.

## Bedeutung für die CI

Wenn ihr euch auf die README verlasst, sendet die Pipeline trotz `CI=true` und `METRIKFUNK_DISABLE=1`. Dabei gehen Hostname und alle `props` an den Endpunkt. Die Angaben unter „Datenschutz“ und „Leistung“ (`README.md:22`) sind Behauptungen des Herstellers, die kein Beleg stützt.

## Empfehlung

Empfohlen ist **integrieren mit Auflagen**, und das nur, wenn ihr das Netz zusätzlich absichert:
1. In der Pipeline `METRIKFUNK_OPTOUT=1` setzen, genau mit dem Wert `1`.
2. Den ausgehenden Verkehr des CI-Jobs zusätzlich sperren, z. B. mit einer Egress-Sperre oder einem Netzwerk-Namespace ohne Route. Das Opt-out hängt an einer einzigen undokumentierten Zeile, die ein Update stillschweigend ändern kann. Mit der Netzsperre hängt „nichts geht nach außen“ nicht mehr allein am Paket.
3. `METRIKFUNK_DISABLE=1` könnt ihr zusätzlich setzen, falls eine spätere Version es tatsächlich umsetzt. Verlassen dürft ihr euch darauf nicht.
4. Bei jedem Update von `vendor/metrikfunk` `telemetryEnabled()` und den Aufbau des Bodys erneut prüfen.

## Offen

- **Noch nicht praktisch geprüft:** Ich habe die Aussagen nur durch Lesen des Codes gewonnen und keinen Test ausgeführt. Ein kleiner Test wäre `track()` einmal mit und einmal ohne `METRIKFUNK_OPTOUT=1` aufzurufen, mit gemocktem `https.request` oder ohne Netzzugang, und dann zu zählen, wie oft `request` aufgerufen wird. Erwartet: mit Opt-out 0 Aufrufe, ohne Opt-out 1 Aufruf.
- Herkunft und Lizenz des Pakets: Im vendor-Verzeichnis gibt es keine LICENSE-Datei. Die README bezeichnet das Paket als „synthetisches Fremdpaket“ (`README.md:4`).
