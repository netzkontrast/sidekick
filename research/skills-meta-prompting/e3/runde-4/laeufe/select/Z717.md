# Recherchebericht: kvstash (vendor/kvstash, v0.4.1) als Sitzungscache

**Gelesener Stand:** Arbeitsbaum (`@arbeitsbaum`). Laut Sitzungskontext lag ein einzelner Snapshot-Commit `1a6c911` mit sauberem Status vor; da ohne Git-Historie gearbeitet wird, belege ich alles gegen den Arbeitsbaum. Ich habe alle vier Dateien unter `vendor/kvstash/` vollständig gelesen. Es wurde nichts ausgeführt, installiert oder geändert.

**Prüffrage:** Erfüllt kvstash beide Anforderungen? (A1) Einträge laufen nach einer in **Sekunden** angegebenen Zeit ab. (A2) Gesetzte Einträge überstehen einen Prozessneustart **ohne zusätzlichen Aufruf**.

## Ergebnis

**Nein. Laut Code ist keine der beiden Anforderungen erfüllt.** Das README verspricht beides, aber der Code macht es anders:

- **A1 nicht erfüllt:** Der Code rechnet `ttl` in **Millisekunden** (`Date.now() + ttl`). Das README-Beispiel `ttl: 3600`, gedacht als eine Stunde, läuft deshalb schon nach 3,6 Sekunden ab. Außerdem gilt `ttl: 0` als „kein Ablauf“, weil die Prüfung `ttl ?` den Wert 0 als falsch behandelt.
- **A2 nicht erfüllt:** `set()` setzt nur `dirty = true` und schreibt nichts auf die Platte. Gespeichert wird erst durch einen ausdrücklichen Aufruf von `flush()`. Es gibt keinen automatischen Flush, keinen Timer und keinen Exit-Hook.
- **Weitere Abweichung:** Das README nennt das Schreiben atomar (temporäre Datei plus Umbenennen). Der Code schreibt aber direkt mit `writeFileSync` in die Zieldatei. Ein Absturz mitten im Schreiben kann die Datei beschädigen. Beim nächsten Start würde `JSON.parse` dann im Konstruktor eine Ausnahme werfen.
- **Nebenbefund:** Abgelaufene Einträge werden in `get()` nur im Speicher gelöscht, `dirty` bleibt dabei unverändert. In der Datei bleiben sie stehen, bis ein anderer `set()` mit anschließendem `flush()` sie mitschreibt.
- **Lizenz:** `package.json` und `LICENSE.txt` nennen MIT. Der Lizenztext ist aber gekürzt und weicht vom MIT-Standardtext ab, unter anderem fehlen der Gewährleistungsausschluss und die Liste der Rechte. Der Rechteinhaber ist als „kvstash contributors (synthetisch)“ angegeben. Die Herkunft ist unklar.

## Bedeutung für die Entscheidung

Nimmt man kvstash unverändert, laufen Sitzungen bei der dokumentierten Nutzung etwa 1000-mal zu früh ab. Ohne eigene Flush-Logik gehen sie außerdem beim Neustart verloren. Der Ticket-Dienst müsste beides selbst ausgleichen: den TTL-Wert mit 1000 multiplizieren und `flush()` nach jedem `set` aufrufen. Selbst dann bliebe das nicht-atomare Schreiben ein Risiko. Dazu kommen die unklare Lizenz bzw. Herkunft und der eingeschleuste Agenten-Hinweis, die das Vertrauen in das Paket zusätzlich schwächen.

## Empfehlungskategorie

**Verhalten neu implementieren.** Die Anforderungen sind klein und klar umrissen: TTL in Sekunden, sofortiges und atomares Speichern bei jedem `set`, robustes Laden. kvstash in der vorliegenden Form zu integrieren, empfehle ich nicht. Die Entscheidung liegt beim Plattform-Team.

## Nächster Schritt / offener Versuch

Kleinster reproduzierbarer Versuch in einem leeren Temp-Verzeichnis, sobald Ausführen erlaubt ist. In dieser Recherche wurde er wegen der Nur-lesen-Regel nicht durchgeführt:

1. Mit `new Stash({file})` ein Objekt anlegen und `set('k', 1, {ttl: 5})` aufrufen.
2. Nach 100 ms `get('k')` lesen. Erwartet ist laut Code `undefined` (Ablauf nach 5 ms), laut README `1`.
3. Ohne `flush()` einen neuen Prozess starten und `get('k')` lesen. Erwartet ist laut Code `undefined`, und die Datei existiert nicht.

Damit würden die Befunde zu A1 und A2 von „im Code gefunden“ auf „praktisch nachgewiesen“ steigen.
