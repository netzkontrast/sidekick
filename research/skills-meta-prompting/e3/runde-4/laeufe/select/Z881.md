# Recherchebericht: kann `vendor/ratezaun` Mandantenlimits über alle drei Instanzen durchsetzen?

## Ergebnis

**Nein.** Am gelesenen Stand erfüllt `vendor/ratezaun` keine der drei Anforderungen:

1. **Gemeinsames Limit über drei Instanzen:** Nicht möglich. Das einzige Backend, das tatsächlich läuft, hält die Zähler nur im Speicher der jeweiligen Instanz. `RedisStore` ist leer und wirft nur einen Fehler.
2. **Keine doppelte Last an Fenstergrenzen:** Nicht erfüllt. Der Code zählt in starren Zeitfenstern, nicht in einem gleitenden Fenster, wie das README behauptet.
3. **Burst:** Nicht vorhanden. Der Parameter `burst` wird angenommen, aber nirgends verwendet.

Ich empfehle, das Verhalten neu umzusetzen oder eine andere Bibliothek zu prüfen. Die Entscheidung trifft die Architekturrunde.

## Praktische Versuche
**Keiner ausgeführt.** Ich hatte in dieser Sitzung kein Shell-Werkzeug, und die Vorgaben schließen das Starten von Diensten aus. Alle Aussagen oben stützen sich auf gelesenen Code. Der kleinste Versuch, der A3, A5 und A9 nachweisen würde, ohne Pakete oder Dienste zu brauchen:
- **Voraussetzung:** Node ≥ 18 und ein Skript außerhalb von `vendor/`, das `src/limiter.js` direkt importiert und mit einfachen `req`/`res`-Attrappen und eingefrorenem `Date.now` aufruft.
- **Ablauf:** `limit=3`, `windowMs=1000`, `burst=2`.
  1. 3 Anfragen bei t=999 ms, dann 3 bei t=1000 ms.
  2. Eine weitere Anfrage bei t=1001 ms.
  3. Eine Anfrage mit `store: new RedisStore({})`.
- **Erwartung laut Code:** In Schritt 1 kommen alle 6 durch (doppelte Last). Die 4. Anfrage im zweiten Fenster bekommt 429, obwohl `burst=2` gesetzt ist. Schritt 3 endet mit dem Fehler „not implemented yet“.
- **Ergebnis:** nicht ausgeführt.

## Was das für die Entscheidung bedeutet
- **Gemeinsames Limit über drei Instanzen:** nicht erfüllt (A5–A7). Es fehlt ein gemeinsamer Zustand, und dieses Backend müsste erst gebaut werden.
- **Keine doppelte Last an Fenstergrenzen:** nicht erfüllt (A2, A3). Nötig wäre ein anderer Algorithmus, etwa ein gleitendes Fenster (Log oder Zähler) oder ein Token-Bucket. Das ist keine Konfigurationsfrage.
- **Burst für kurze Lastspitzen:** nicht erfüllt (A9). Ein Token-Bucket würde Burst und gleichmäßige Rate zusammen abdecken.
- **Zuverlässigkeit der Doku:** Drei von vier README-Versprechen werden vom Code nicht gehalten. Deshalb sollte auch Upstream-Doku dieser Bibliothek nur nach Prüfung des Codes geglaubt werden.

## Empfehlungskategorie (keine Entscheidung)
**Verhalten neu umsetzen**, oder eine andere, geprüfte Bibliothek auswählen. In beiden Fällen braucht es einen gemeinsamen Speicher mit atomarer Operation, z. B. ein Redis-Skript für einen Token-Bucket oder ein gleitendes Fenster je Mandant.

Ob dafür eine neue Abhängigkeit (Redis-Client, externe Bibliothek) hinzukommt, entscheidet laut AGENTS.md die Architekturrunde.

Von „integrieren“ oder „Dependency nutzen“ für `ratezaun` 1.2.0 rate ich ab. „Zurückstellen“ ergibt nur Sinn, wenn Upstream eine neuere Version mit fertigem `RedisStore` und Burst hat. Das ist **offen**, weil die Upstream-Quelle unbekannt ist.
