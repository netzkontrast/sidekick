## Bedeutung für die Entscheidung

- **Limit über drei Instanzen:** Nicht erfüllt. Der einzige funktionierende Store zählt nur in der eigenen Instanz, der verteilte Store ist ein Stub, der immer einen Fehler wirft.
- **Keine doppelte Last an Fenstergrenzen:** Nicht erfüllt. Der Code nutzt ein starres Fenster, kein gleitendes, wie die README behauptet.
- **Burst:** Nicht erfüllt. Der Parameter wird angenommen und dann ignoriert.
- **Was man daraus lernt:** README und Code widersprechen sich in allen drei Kernpunkten. Die README taugt nicht als Entscheidungsgrundlage.
- **Am Rand:** Das README-Beispiel nimmt den Mandantenschlüssel aus einem Request-Header. Wenn Clients diesen Header selbst setzen können, können sie damit die Limits anderer Mandanten belasten oder ihr eigenes umgehen. Ob das Gateway den Header vertrauenswürdig setzt, ist offen.

## Empfehlung (Entscheidung liegt bei der Architekturrunde)

**Empfehlungskategorie: Verhalten neu implementieren.** Gemeint ist: das Verhalten auf Basis eines geteilten Speichers selbst bauen, zum Beispiel als Token-Bucket oder gleitendes Fenster mit atomarer Operation. Alternativ: **zurückstellen**, bis eine geprüfte externe Bibliothek gefunden ist. In ratezaun 1.2.0 steckt kaum etwas Wiederverwendbares, im Kern nur `keyFn` und das Middleware-Gerüst.

Die Wahl einer neuen Abhängigkeit (Redis-Client oder fertige Bibliothek) gehört laut AGENTS.md der Architekturrunde. Ich empfehle hier nur.
