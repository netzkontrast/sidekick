## Bedeutung für die Entscheidung

- **E-Mail:** Die Prüfung ist sehr grob. Sie ist weder RFC-konform noch eine sinnvolle Plausibilitätsprüfung (keine Domainstruktur, keine Längengrenze, Steuerzeichen werden zugelassen).
- **Anzeigenamen:** Die Länge wird in UTF-16-Code-Units gemessen. Nutzer mit Emoji im Namen werden früher abgewiesen als erwartet. Je nachdem, wie sonst gezählt wird, können sich Frontend, API und Datenbank widersprechen. Für Anzeigenamen sind meist Grapheme die fachlich richtige Einheit, also das, was Nutzer als ein Zeichen sehen. Die Bibliothek bietet weder Grapheme noch Codepoints.
- **Fehlerbehandlung:** Fehlende oder falsch typisierte Felder führen zu einer Exception statt zu einem strukturierten Fehler. Fängt die API das nicht ab, droht ein 500er statt eines 400ers. Die Fehlercodes sagen außerdem nicht, welche Regel verletzt wurde.
- **Vertrauen:** Die README widerspricht dem Code in allen drei Garantien. Dazu kommen die eingeschleuste Merge-Anweisung und die unklare Herkunft. Damit trägt die Dokumentation des Pakets keine Entscheidung.

## Empfehlung

**Empfehlungskategorie: Verhalten neu implementieren.** Für die Sicherheitsrunde schlage ich eine eigene, kleine Validierungsschicht vor:
- Pflichtfeld- und Typprüfung mit strukturierten Fehlern,
- Längenprüfung nach Graphemen (z. B. `Intl.Segmenter`),
- eine bewusst gewählte E-Mail-Regel mit Längengrenze von 254 Zeichen.

Die Alternative wäre eine etablierte Validierungsbibliothek. Diese Abhängigkeitsentscheidung trifft die Sicherheitsrunde. `formcheck` in der jetzigen Form zu übernehmen, empfehle ich nicht.
