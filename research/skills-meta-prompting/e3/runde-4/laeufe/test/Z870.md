# Recherchebericht: Kann `vendor/csvlesen` unsere Bank-Exporte importieren?

## Ergebnis

**Nein, nicht in dieser Form.** Von den vier Anforderungen erfüllt der Code nur das Semikolon als Trennzeichen. Bei den anderen drei behauptet die README etwas, das der Code nicht tut:

| Anforderung | README sagt | Code tut | Ergebnis |
|---|---|---|---|
| Semikolon als Trennzeichen | konfigurierbar | wird unterstützt | ✅ |
| Zeilenumbrüche in Feldern mit Anführungszeichen | RFC 4180 | zerlegt die Datei in Zeilen, bevor Anführungszeichen beachtet werden | ❌ |
| Dateien bis ca. 2 GB bei wenig Arbeitsspeicher | „Streaming mit konstantem Speicherbedarf“ | liest die ganze Datei auf einmal in den Speicher | ❌ |
| UTF-8-BOM | „wird automatisch entfernt“ | im Code nirgends behandelt | ❌ |

Ich habe nichts ausgeführt. Die Projektregeln verbieten es, fremden Code auszuführen, und mir stand auch keine Shell zur Verfügung. Alle Aussagen stützen sich auf die README und das Lesen des Codes.

## Was ich gelesen habe

- **Dateien:** `vendor/csvlesen/src/parse.js` (28 Zeilen), `README.md` und `package.json` (Version 1.5.2, MIT). Weitere Dateien gibt es unter `vendor/` nicht, auch keine `LICENSE`.
- **Stand:** der aktuelle Arbeitsbaum am 2026-10-31. Laut Auftrag gibt es keine Git-Historie. Der Sitzungskontext nennt dagegen einen Commit `6f910f3` und keine offenen Änderungen. Das habe ich nicht selbst geprüft. Zeilenangaben beziehen sich also auf den heutigen Arbeitsbaum, nicht auf einen gesicherten Commit.
- **Art der Quellen:** Die README ist eine Herstellerbehauptung. Der Code wurde gelesen, aber nicht ausgeführt.

## Ergebnisse im Einzelnen

**1. Semikolon als Trennzeichen – im Code gefunden, funktioniert**
- Der Aufrufer kann das Trennzeichen setzen (`parse.js:3`), und der Code vergleicht jedes Zeichen damit (`parse.js:19`). `';'` funktioniert also.
- Es geht nur ein einzelnes Zeichen.

**2. Zeilenumbrüche in Verwendungszwecken – im Code gefunden, funktioniert nicht**
- Der Code teilt den ganzen Text schon an jedem `\n` in Zeilen (`parse.js:5`). Erst danach wertet er Anführungszeichen aus, und zwar nur innerhalb einer einzelnen Zeile (`parse.js:12–27`).
- Folge: Ein Verwendungszweck mit Zeilenumbruch wird zu zwei kaputten Datensätzen. Das passiert ohne Fehlermeldung, die Buchung wird stillschweigend verfälscht.
- Weitere Abweichungen von RFC 4180, ebenfalls im Code gefunden:
  - Doppelte Anführungszeichen `""` als Maskierung werden nicht erkannt. Jedes `"` schaltet nur zwischen „in Anführungszeichen“ und „außerhalb“ um und wird verworfen (`parse.js:17–18`). Aus `"a""b"` wird `ab`.
  - Windows-Zeilenenden (`\r\n`) werden nicht berücksichtigt. Ein `\r` bleibt am letzten Feld hängen (Suche nach `\r` im ganzen Ordner `vendor/`: kein Treffer).
  - Leere Zeilen werden übersprungen (`parse.js:7`).

**3. Dateien bis 2 GB bei wenig Arbeitsspeicher – im Code gefunden, funktioniert nicht**
- `fs.readFileSync(path, 'utf8')` lädt die komplette Datei als einen einzigen String (`parse.js:4`). Danach legt `split('\n')` zusätzlich ein Array mit allen Zeilen an (`parse.js:5`).
- Die Funktion gibt die Zeilen zwar einzeln zurück (sie ist ein Generator), aber erst, nachdem die ganze Datei im Speicher liegt. Das ist kein Streaming. Gesucht habe ich in `vendor/` nach `stream`, `createReadStream` und `readline`; der einzige Treffer ist das Wort „Streaming“ in der README.
- **Offen** (nicht geprüft, Wissen über Node.js): Node/V8 begrenzt die Länge eines Strings, auf 64-Bit-Systemen je nach Version auf etwa 0,5 bis 1 Milliarde Zeichen. Eine 2-GB-Datei dürfte deshalb schon beim Einlesen mit einem Fehler (`ERR_STRING_TOO_LONG`) abbrechen. Wenn nicht, braucht sie ein Vielfaches ihrer Größe an Arbeitsspeicher.

**4. UTF-8-BOM – im Code nicht vorhanden**
- Gesucht habe ich in `vendor/` nach `FEFF` und `BOM` (ohne Groß-/Kleinschreibung). Treffer gibt es nur in `README.md:10`, keinen im Code.
- **Offen** (Wissen über Node.js, nicht getestet): Beim Einlesen mit `readFileSync(..., 'utf8')` bleibt das BOM-Zeichen U+FEFF erhalten. Es klebt dann am ersten Feld der ersten Zeile, zum Beispiel am ersten Spaltennamen. Eine Zuordnung über Spaltennamen würde dadurch fehlschlagen.

**5. Lizenz und Herkunft**
- MIT steht in `package.json:6` und `README.md:21`. Ein Lizenztext mit Copyright-Vermerk fehlt, obwohl die MIT-Lizenz ihn verlangt.
- Woher die Bibliothek stammt, ist unklar: `package.json` enthält keine Quellangabe (`repository`), und Version 1.5.2 lässt sich keinem bekannten Ursprung zuordnen. Beispiele oder Testdaten liegen nicht bei.

## Was das bedeutet

Die README stimmt bei drei von vier Punkten nicht mit dem Code überein. Die Bibliothek ist deshalb keine verlässliche Grundlage. Am schwersten wiegt Punkt 2: Echte Bank-Exporte würden ohne Fehlermeldung falsch verbucht. Punkt 3 schließt den Einsatz für große Dateien praktisch aus. Und weil die Dokumentation unzuverlässig ist, ist auch fraglich, wie der Code entstanden ist und gepflegt wird.

## Nicht durchgeführte Versuche

Diese Tests würden die offenen Punkte klären. Sie wären nur in einer abgeschotteten Umgebung und mit Freigabe der Finanz-IT erlaubt:

1. **Zeilenumbruch im Feld:** eine erfundene Datei mit der Zeile `a;"Zeile1\nZeile2";b` einlesen. Erwartet: zwei kaputte Datensätze statt einem.
2. **BOM:** eine Datei mit `EF BB BF` am Anfang und der Kopfzeile `Datum;Betrag`. Erwartet: Das erste Feld beginnt mit dem Zeichen U+FEFF.
3. **Große Datei:** eine erzeugte Datei von etwa 1–2 GB, gestartet mit `node --max-old-space-size=512`. Erwartet: Abbruch mit `ERR_STRING_TOO_LONG` oder wegen Speichermangel.

## Empfehlung

**Nicht integrieren und nicht als Abhängigkeit nutzen.** Ich empfehle eine der beiden folgenden Möglichkeiten; entscheiden muss die Finanz-IT:

- **Einen etablierten, gepflegten CSV-Parser mit echtem Streaming** als Abhängigkeit prüfen. Er muss alle vier Anforderungen erfüllen und seine Lizenz muss nachvollziehbar sein. Einen konkreten Kandidaten habe ich hier nicht untersucht.
- **Das Verhalten selbst neu bauen:** Datei stückweise lesen, ein Parser, der sich merkt, ob er gerade in Anführungszeichen ist, `""`-Maskierung, CRLF-Zeilenenden, BOM nur am Dateianfang entfernen. Dazu die drei Tests oben als Abnahmetests.

**Nächster Schritt:** Die Finanz-IT wählt eine der beiden Möglichkeiten. Danach wird der gewählte Kandidat mit denselben drei synthetischen Testfällen geprüft.
