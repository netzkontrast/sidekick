## Bedeutung

- **Startzeit:** Die Anforderung ist nicht erfüllt. Mit 5-Feld-Ausdruck `30 2 * * *` startet der Lauf um 02:30 UTC und damit je nach Jahreszeit eine bzw. zwei Stunden zu spät. Die Option `tz` wird stillschweigend ignoriert. Der 6-Feld-Ausdruck aus dem README führt sofort zu einem Fehler. Ein Workaround über `TZ=Europe/Berlin` für den Prozess wäre nur eine Vermutung. Er ist ungetestet und würde außerdem die Frage nicht lösen, was bei der Umstellung passiert: Am Umstellungstag im Frühjahr gibt es 02:30 Uhr gar nicht, im Herbst gibt es die Uhrzeit zweimal.
- **Überlappung:** Die Anforderung ist nicht erfüllt. Der dokumentierte Schutz fehlt im Code.
- **Lizenz:** Die Angaben widersprechen sich. Die Rechtsabteilung sollte die Lizenz als ungeklärt behandeln, bis die Herkunft feststeht. Das gilt getrennt für Code (`src/schedule.js`), Dokumentation (README) und Metadaten (`package.json`). Beispiele oder Daten enthält das Paket nicht.
- **Insgesamt:** Die README beschreibt Funktionen, die der Code nicht hat. Deshalb sollte man auch den übrigen Angaben der Bibliothek nicht ohne Prüfung trauen.

## Empfehlung (die Entscheidung liegt bei der Teamleitung Betrieb)

**Kategorie: zurückstellen.** Als Alternative: **Verhalten neu implementieren** oder auf einen geprüften Scheduler setzen. Dazu gehören eine echte Zeitzonen-Auflösung für `Europe/Berlin`, festgelegte Regeln für die Umstellungstage und eine Sperre über Prozessgrenzen hinweg (z. B. ein Lock in der Datenbank oder einer Datei), nicht nur ein Flag im Speicher.

## Nächste Schritte

1. **Rechtsabteilung:** Herkunft von `vendor/zeitplan` klären (Upstream-Repository, Version 0.9.0, vollständiger Lizenztext, NOTICE-Datei). Bis dahin die Lizenz als ungeklärt behandeln.
2. **Offener Versuch:** Falls eine Ausführung freigegeben wird, folgendes in einer isolierten Umgebung mit vorgestellter Uhr testen:
   - `schedule('0 30 2 * * *', …)`: Erwartung laut Code ist ein Fehler wegen der Feldanzahl.
   - `schedule('30 2 * * *', job, { tz: 'Europe/Berlin' })` mit `TZ=UTC`: Erwartung laut Code ist ein Start um 02:30 UTC.
   - Ein Job mit mehr als 24 h Laufzeit: Erwartung laut Code ist ein zweiter, paralleler Start.

   Diese Tests würden die Befunde aus dem Code praktisch nachweisen. Für die Entscheidung gegen den Einsatz sind sie aber nicht nötig.
3. **Nur falls die Teamleitung die Bibliothek trotzdem weiterverfolgen will:** einen Behavior-Spec für die Umstellungstage (letzter Sonntag im März und im Oktober) und für die Sperre gegen parallele Läufe schreiben, bevor implementiert wird.
