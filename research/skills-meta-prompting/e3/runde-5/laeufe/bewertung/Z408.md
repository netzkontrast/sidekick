# Recherchebericht: `vendor/eanpruef` (Version 1.2.0) für die EAN-Prüfung im Wareneingang

**Kurzantwort:** Nein, in beiden Punkten. Die Bibliothek weist falsch gelesene Codes nicht ab, obwohl die README das behauptet. EAN-8-Codes lehnt sie grundsätzlich ab, auch gültige. GS1 Digital Link ist im Code nicht vorhanden, es gibt dafür nur einen Roadmap-Eintrag ohne Termin. Als Lösung für 2027 kommt sie daher nicht in Frage, und für den Wareneingang taugt sie in dieser Form auch jetzt nicht.

## Prüffrage und Annahmen
- **Zu entscheiden ist:** Darf `eanpruef` in diesem Stand vor dem Buchen im Wareneingang prüfen, und taugt sie auf Dauer (GS1 Digital Link ab 2027)?
- **Annahme 1:** Gemeint ist die öffentliche Funktion `isValidEan`, auf die `main` zeigt (`vendor/eanpruef/package.json:6@arbeitsbaum`). Eine andere Prüffunktion wird nicht exportiert (Suche nach `export` in `vendor/eanpruef/`).
- **Annahme 2:** „Falsch gelesen“ heißt: Die Ziffernzahl stimmt, aber einzelne Ziffern sind falsch oder vertauscht. Genau solche Fehler soll eine Prüfziffer erkennen.
- **Annahme 3:** Ob es neuere Versionen außerhalb von `vendor/` gibt, habe ich nicht geprüft. Es gab keine Internetrecherche, gelesen wurde nur der Arbeitsbaum.
- **Einschränkung:** Ich hatte in dieser Sitzung keine Möglichkeit, Befehle auszuführen. Deshalb gibt es keinen ausgeführten Test. Alle Aussagen zum Verhalten beruhen auf dem Lesen des Codes.

## Bewertung
- **Fehlerhafte Codes werden nicht zuverlässig abgewiesen.** Die Prüfziffer wird nie geprüft, und EAN-8 wird komplett abgelehnt. Im Wareneingang würden dadurch falsch gelesene EAN-13 gebucht. Gültige EAN-8 würden abgewiesen, was Nacharbeit oder Umgehungen verursacht. Die README gibt hier einen Stand an, den der Code nicht hat.
- **Digital Link ab 2027:** Dafür gibt es nur eine Absichtserklärung ohne Code und ohne Termin. Nach `AGENTS.md` taugt so eine Bibliothek höchstens als Übergangslösung. Und selbst dafür reicht sie in diesem Stand nicht, siehe oben.
- **Brauchbarer Teil:** Nur `checkDigit` ist laut Code-Lektüre korrekt (bis auf die fehlende Eingabeprüfung). Eine eigene Prüfung ist klein: Länge 8 oder 13, nur Ziffern, Prüfziffer vergleichen. Dafür braucht man die Bibliothek kaum.
- **Lizenz:** Wegen des verkürzten Lizenztexts sollte die Rechtsabteilung kurz draufschauen, bevor Teile übernommen werden.

## Empfehlung
**Kategorie: Verhalten neu implementieren.** Die EAN-8/13-Prüfung samt Prüfziffer sollte im eigenen Code entstehen, eventuell angelehnt an `checkDigit`. `eanpruef` sollte nicht als Dependency eingebunden werden. Für GS1 Digital Link wird eine eigene Bibliotheksrecherche gebraucht, das ist ein eigener Punkt mit Ziel 2027. Entscheiden muss die Lagerleitung.

**Nächster Schritt (noch offen):** Ein kleiner Test sollte die Befunde aus dem Code bestätigen. Nur lesend, ohne Installation, aus einem Skriptverzeichnis außerhalb von `vendor/`, zum Beispiel:
```
node --input-type=module -e "import {isValidEan} from '<abs>/vendor/eanpruef/src/validate.js'; console.log(isValidEan('4006381333931'), isValidEan('4006381333932'), isValidEan('96385074'))"
```
- **Erwartet laut Code:** `true true false`
- **Richtig wäre:** `true false true`

Danach würde ich eine Spezifikation der Eingangsprüfung schreiben (Skill specifying-behavior), mit Fehlerfällen wie Leerzeichen, falscher Länge, Nicht-Ziffern und falscher Prüfziffer.
