## Warum höchstens at-least-once

- **Doppelte Wirkung:** Eine Aufgabe kann ihre Wirkung schon erzielt haben und dann vor dem Wechsel auf `done` abstürzen. Sie steht dann noch auf `running` und läuft ein zweites Mal. Für Idempotenz gibt es keinen Mechanismus: keinen Schlüssel, keinen Ergebnis-Check und keinen Zähler für Versuche (`jobs.py:2-3`).
- **Kein Schutz für Aufgaben, die gerade laufen:** Es gibt kein Lease, keinen Heartbeat, kein Fencing und keine Prüfung, welcher Worker die Aufgabe hat. Wenn `resume()` startet, während ein anderer Prozess noch arbeitet, werden dessen Aufgaben ebenfalls zurückgesetzt. Sie laufen dann womöglich gleichzeitig doppelt.
- **Keine Transaktion um die Schleife:** Ein Absturz mitten in `resume()` ist trotzdem harmlos, weil das Update beim nächsten Lauf einfach erneut ausgeführt werden kann.
- **Nicht belegt:** ob aus `queued` überhaupt wieder eine Ausführung wird, wann eine Aufgabe auf `running` gesetzt wird und ob dabei committet wird. Dieser Code fehlt (Befund 3). „at-least-once“ ist deshalb eine Obergrenze und keine zugesicherte Eigenschaft.

**Widerspruch:** Das README sagt „startet erneut“ (`README.md:9`). Der Code stellt die Aufgaben aber nur zurück in die Warteschlange (`jobs.py:3`).
