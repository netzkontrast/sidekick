## Ergebnis zu vendor/ratelimitd (Stand: Commit `aa9e6f7`, Paketversion 0.4 laut README)

**Algorithmus: Token Bucket.** Das habe ich im Code gefunden und nicht nur aus der Dokumentation übernommen. In `vendor/ratelimitd/limiter.py:3` ist die Klasse `TokenBucket` definiert, die Logik steht in `limiter.py:15-22`:
- Bei jedem Aufruf von `allow()` wird der Bestand anhand der verstrichenen Zeit aufgefüllt (`(now - self.last) * self.rate`, höchstens bis `capacity`).
- Ist mindestens ein Token vorhanden, wird eines abgezogen und `True` zurückgegeben, sonst `False`.
- Die Zeit kommt aus `time.monotonic()`. Sprünge der Systemuhr stören den Limiter also nicht.
- Am Anfang ist der Bucket voll (`limiter.py:13`). Direkt nach dem Start lassen sich also bis zu `capacity` Anfragen auf einmal durchlassen.

**Mehrere Prozesse teilen sich keinen gemeinsamen Zähler.** Auch das ist im Code gefunden und deckt sich mit der Dokumentation:
- Der Docstring in `limiter.py:4` sagt ausdrücklich: „Zustand liegt nur im Speicher dieses Prozesses.“
- Der Code bestätigt das. Der Zustand besteht nur aus den Instanzattributen `tokens` und `last` (`limiter.py:13`). Ich habe in den beiden vorhandenen Dateien (`README.md`, `limiter.py`) auf diesem Commit nach Shared Memory, Datei, Redis, Socket und ähnlichen Mechanismen gesucht und keine gefunden.
- In der Praxis heißt das: Bei N Worker-Prozessen (etwa gunicorn mit mehreren Workern) gilt das Limit pro Prozess. Insgesamt kommen also bis zu N × `rate`, beim Start sogar N × `capacity` Anfragen durch.

**Weitere Einschränkung (im Code gefunden):** `allow()` verwendet keinen Lock. Wenn mehrere Threads im selben Prozess dieselbe Instanz nutzen, sind Race Conditions möglich. Unter Last kann dann gelegentlich mehr durchgelassen werden, als das Limit erlaubt.

**Lizenz:** Das README nennt MIT. Eine eigene LICENSE-Datei liegt nicht bei, und die Herkunft des Pakets ist im Repo nicht belegt.

**Noch offen:** Ich habe nichts ausgeführt. Mit einem kleinen Test ließe sich das Verhalten über mehrere Prozesse belegen: zwei Prozesse mit je `TokenBucket(rate=1, capacity=1)` gleichzeitig `allow()` aufrufen lassen. Erwartet wird, dass beide `True` bekommen.

**Was das für die Entscheidung heißt:** Soll das Limit pro Instanz gelten, ist das Paket brauchbar. Wenn ihr ein globales Limit über mehrere Worker oder Hosts braucht, reicht es so nicht.

**Empfehlung:** Für ein globales Limit würde ich das **Verhalten neu implementieren**, also einen Token Bucket mit gemeinsamem Speicher, zum Beispiel ein atomares Redis-Skript. Gilt das Limit nur pro Prozess, könnt ihr es **als Dependency nutzen**, solltet aber einen Lock für den Einsatz mit mehreren Threads ergänzen.
